# Artifree PR 로드맵

기준: 2026-11-10, R09d3 구현과 [0051](decisions/0051-roadmap-and-architecture-review.md)의
재검토까지 반영한 계획이다. 목표는 외부 agent로 아티팩트를 만들고 편집하며,
로컬·사설 서버에서 계속 사용할 수 있는 작업공간이다. 아래 ID는 계획 식별자이며
GitHub PR 번호가 아니다. 각 행의 상태는 구현과 후속 범위를 구분한다. 각 행은
별도로 검토·병합할 구현 PR의 출발점이고, PR 구성은 그 트랙을 시작하거나 진행하면서
다시 정한다.

완료한 범위는 A01–A11, O01·O02·O03a·O03b·O03d·O04–O08, R01·R04–R07·R06b·R08a·R08b·
R09·R11a·R11b·R12·R13, S01, X01이다. 남은 범위와 권장 순서는
[실행 순서와 도달 지점](#실행-순서와-도달-지점)에 있다. 선행 조건이 없는 작업
사이에는 순서를 바꿀 수 있다.

## 모든 구현 PR의 진입 조건과 완료 기준

1. 관련 최신 REA 분석과 후속 정정을 읽고, 결론에 연결된 원본 소스·trace·요청/응답·
   실제 출력 파일을 대조한다. 관찰 사실, 원본 코드에서만 확인한 사실, 추론,
   Artifree 자체 결정을 구분한다. 초기 설계보다 최신 관찰 계약과 후속 검증을 우선한다.
2. 공개 결정 기록에 요구사항과 선택 근거를 남긴다. 로컬 비공개 추적표에는
   `요구사항 ID → REA 보고서 → 원본 파일/버전/hash/JSON 위치 → 구현 → 테스트`를
   연결한다. 표에 적힌 참조만으로 원본 검토가 끝났다고 처리하지 않는다.
3. 소스 리비전, 문서 node revision/sequence, 앱 데이터 version, 권한 version,
   게시 대상, job 상태를 별도로 다룬다. 저장·공개·화면 반영·외부 효과의 완료를 구분한다.
4. 정상 흐름과 함께 거절·충돌·재시도·중단·복구를 검증한다. 중요한 방어 검사는
   실제로 깨뜨렸을 때 실패함을 확인하고 복구한다. 실제 provider·브라우저·agent 실행과
   대체 fixture의 결과를 구분한다.
5. `npm run check`, `npm run build`와 관련 통합 검사를 통과시킨다. UI/HTML 변경은
   Chromium smoke를 실행하고 CI가 Firefox에서도 실행한다. 계약·경계·목록·설계 변경을 함께 갱신하고, 그 외의 기존 CI를
   약화하지 않는다. 원본 비교 예시도 독립 작성한 입력을 사용한다.
6. 하나의 관찰 가능한 결과를 검토할 수 있게 만든다. 빈 port, 범용 wrapper,
   placeholder 테스트만 추가하는 PR을 먼저 만들지 않는다. 실제 diff가 여러 독립 기능으로
   커지면 이 계획 ID에 하위 ID를 붙여 분리하고 선행 관계를 갱신한다.

구현 입력 제한은 원본 DLL을 실행 엔진으로 쓰지 않는 것이다. 기존 인계와 참조 명세·분석
작업 공간의 이전 구현 입력 제한을 대체한다. 인증 정보·로컬 데이터·비공개 증거와 그
경로·생성된 검증 출력·캐시는 공개 저장소에 넣지 않는다. PR마다 Codex 리뷰 1회와
구현자의 대화 이력이 없는 독립 subagent 리뷰 1회를 수행하고, 지적을 처리한 뒤 추가
리뷰 없이 관련 검사를 실행한다. 이전 3회 리뷰·실패 시 폐기와 재구현 규칙은 적용하지
않는다. 리뷰의 기한·기록·병합 조건은 [기여 지침](../.github/CONTRIBUTING.md)을 따른다.
원본을 읽어 동작을 파악하는 것과 정식 clean-room 인적 분리의 성립은 구분한다.
실행 문맥이 없어 확인하지 못한 원본 동작은 Artifree 결정으로 명시한다. 특히 별도
원본 계정이 없다는 이유로 Artifree 자체의 두 사용자 권한 테스트를 생략하지 않는다.

### A 트랙 완료 범위와 다음 선택

A01–A11은 단일 owner의 HTML 작업공간 범위로 완료했다. A08에 필요한
R04(runtime metadata 읽기)와 R05(최소 권한 부여·철회)도 구현했다.
등록된 MCP inbox로 선택 영역을 보내고 수신 확인을 받는 경로를 검증했으며,
실제 외부 모델의 수정 완료와 Pi 실행은 미검증이다. inbox는 프로세스 내 상태이고

결정 기록으로 남긴다.

### R08c의 내부 unknown/rejection 재개 부분 구현

기존0041 규칙 11·16·17에 따라, 이전부터 `prepared`였고 durable ACK가 없는
head가 후행 확정 거절을 받아도 `retry_paused`의
`unresolved_after_rejection`과 기존 명시적 `DeliveryResumeSelection`을 유지한다.
실패 횟수나 epoch 초기화는 이전 전송의 불확실성을 지우지 않는다. 새로 준비한
첫 시도의 확정 거절은 기존 blocked 동작을 유지하며, 실제 same-key replay
receipt는 정상 durable ACK/trim 경로를 따른다. 후행 거절·pause capture 실패·
늦은 authority 상실에도 저장 행과 accounting을 보존한다.

이는 내부 fixed-owner host의 작은 후속 구현이다. 공개 handle·sender 활성화,
generation 재인가·복구 continuation과
native-process 복구는 여전히 미완료다(`discardRejected`는 R08c-3a로,
`abandonUnresolved`는 R08c-3b로 내부 scheduler에만 구현되었고 공개 handle과
연결되지 않았다). 기존0041 번호 규칙이나0047의 폐기
정책을 바꾸지 않는다.

필요하므로 3번을 막지 않는다.
